## 2. 現状と採用した設計方針

既存の`parseCommandArgs`、`isEmpty`、`TimeProvider`、`StorageOperator`を利用する。editの処理・振り分け・helpは未実装。`resolveId`は現在`strconv.Atoi`のみで、0以下の拒否が必要。JSON保存は一時ファイルとrenameを使っており、本Issueで保存方式を変更する必要はない。本番依存パッケージは追加しない。

| 判断 | 選択肢と影響 | 採用案 |
|---|---|---|
| 未指定の表現 | `string`と指定済み`bool`は明示的だが値と状態が別々になる。`*string`はnilで未指定、非nilで空文字を含む指定を表せるが、ポインタの理解が必要。 | CLIで`FlagSet.Visit`から指定の有無を取り、編集用の構造体の`*string`へ変換する。ドメインへFlagSetを渡さない。 |
| 更新方法 | 入力スライスの直接更新は割り当てが少ない。コピーして更新結果を返す方法は割り当てが増えるが、元の一覧を維持でき、既存の`BuildDeletedMemos`と揃えやすい。 | コピーした一覧を返す。Memoは現在値型のフィールドだけなので浅いコピーで足りる。 |
| 入力検証の責務 | CLIとドメイン双方で検証すると安全性は増すが重複する。既存構成に合わせればCLIで入力規則、ドメインで探索・更新に分けられる。 | CLIで指定有無・タイトル・正のIDを検証し、ドメインで対象探索とフィールド・日時更新を行う。ドメインの入力前提を明記する。 |

処理の流れは「引数検証 → Load → 編集時刻を取得 → ドメインで更新結果を構築 → Save → 終了コード0」。異常時はその場で終了コード1を返す。helpは0で終了し、Load/Saveを呼ばない。関数名や構造体名の最終決定は実装時に行う。

## 4. テストで押さえる境界

- 成功系: 非空本文から空本文への変更、空白・複数行本文、前後に空白のある有効タイトルをそのまま保存。タイトルのみ・本文のみでは他項目を維持し、両方指定でも同値指定でもUpdatedAtを編集時刻にする。成功時stdout/stderrは空、終了コード0。
- 時刻: 作成時刻T0と編集時刻T1を異なる固定値にする。既存fakeは常に同じ値を返すため、テスト用に時刻を指定できるfakeを用意する。sleepや実時計に依存せず、CreatedAt=T0、UpdatedAt=T1を比較する。
- 入力: オプション未指定、空/空白のみタイトル、タイトル不正と有効本文の同時指定、未知オプション、ID不足/余分、オプション値不足、非数値・0・負数ID。入力エラーではLoad/Saveを呼ばず、既存ファイルも変更しない。
- 引数構文: `edit 1 --body x`、`edit --body x -- 1`は成功。`edit --body x 1`は既存規則どおり拒否。文字列`--`は`edit 1 --body=--`で保存し、独立した`--`の規則は変更しない。
- help: `edit --help`/`edit -h`はstderrにusageと両オプションを出して0。構文エラーはstderrにusageを出して1。意味的入力エラーの文言は既存の方針に合わせ、Specが固定した文言以外を仕様追加しない。
- 対象なし: 正の未登録ID、および空一覧で`memo not found: <id>`、終了コード1、Saveなし。
- I/O失敗: Load失敗はSaveなし。Save失敗はstderrへ保存失敗を出して1、成功扱いしない。fakeの呼び出し回数を確認する。入力不正・対象なしの実ファイルは前後をバイト比較する。保存途中の各障害での原本・一時ファイル保全は#27のAC-28で検証する。
- 結合: 編集前の本文にだけ含む語と編集後の本文にだけ含む語を使い、更新後の本文検索を確認。新しいCommandから読み直し、同一オブジェクト内の状態だけで合格させない。

## 5. 検証とTDD例外

